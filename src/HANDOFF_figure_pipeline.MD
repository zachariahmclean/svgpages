# Context handoff: publication figure pipeline

Written for a fresh session to pick up where this conversation left off.
User: Zach (zmclean@broadinstitute.org), Windows 11, R/ggplot2 for figure
generation, Inkscape for figure layout/assembly. Single author on this repo
so far, no collaborators yet. Target journal not yet decided.

## Goal

Organize figures for a new publication so that: figures generated by code
across several different project repos can be linked/interacted with from
a central assembly document; updating a figure's underlying code and
re-exporting should be able to refresh the assembled document with minimal
manual rework; final layout is arranged in Inkscape using its "Pages"
feature (one page per figure, or per multi-panel figure).

## Decisions made so far

- **Central `paper_figures/` git repo**, separate from each analysis
  project's own code repo. Each project keeps its plotting code where it
  already lives; only the *rendered output* gets copied/exported into this
  shared repo. This repo also doubles as the "source data" package many
  journals want alongside a submission.
- Directory convention:
  ```
  paper_figures/
    fig1/
      fig1.svg        <- what Inkscape links to
      fig1_data.csv   <- optional underlying data
      SOURCE.md       <- pointer to the originating project/script (since
                          the actual code lives in a different repo)
    fig2/
      ...
    assembly.svg      <- master Inkscape file, uses Pages, one per figure
    figstyle.R        <- shared ggplot2 style module (see below)
    .gitignore
    manuscript.docx   <- fine to keep in the same repo (see caveats below)
  ```
- Each source project gets a "final export" step (a script/notebook
  cell/Makefile target) that always writes its figure to the same path in
  `paper_figures/<fig_id>/<fig_id>.svg`. Rerunning it after an analysis
  change is the manual "this figure changed" trigger -- intentionally
  manual, not auto-triggered, so nothing changes in the manuscript without
  the user noticing.
- **Script organization**: one script per figure (not one giant script,
  not one script per tiny sub-panel) -- keeps the Inkscape hyperlink
  honest (points at exactly the file that made that exact figure), keeps
  git blame clean, keeps runtime fast. Exception: if a figure has multiple
  panels sharing one expensive upstream computation, compute once, cache
  the intermediate result, then plot/save each panel from the cache
  (rather than recomputing per panel, which risks panels drifting out of
  sync too).
- **Word (.docx) manuscript file living in the same git repo**: fine,
  keep it. Caveats: git can't produce meaningful diffs for binary files
  (a text-converter diff driver via pandoc/docx2txt can help --
  `*.docx diff=word` in `.gitattributes` + `git config diff.word.textconv
  "pandoc --to=plain"`); merge conflicts are a real risk *if* more than
  one person edits it (not a concern currently, single author); add Word's
  lock files to `.gitignore` (`~$*.docx` etc. -- already created).

## Key technical findings (Inkscape figure-linking landscape)

1. **Inkscape "Link" import** (File > Import, uncheck Embed): creates an
   `<image>` element referencing the external file. Auto-reloads if
   Preferences > Bitmaps > "Automatically reload linked images when file
   is changed on disk" is enabled. BUT it rasterizes the linked content --
   both on canvas and, critically, in the final PDF export. This is a
   long-standing, still-open Inkscape limitation (since ~2007):
   - https://gitlab.com/inkscape/inbox/-/issues/2103
   - https://gitlab.com/inkscape/inbox/-/issues/2112

2. **Inkscape "Embed"/"Include as editable object(s)"**: converts to true
   native vector paths, fully editable -- but it's a one-time disconnected
   copy. No link back to the source file, no update mechanism at all.

3. **PDF/EPS import in Inkscape has no link option whatsoever** -- it's
   always "include" (one-time vector conversion), even worse than SVG for
   this use case since there's no linking mechanism to even consider.
   Known gap: https://gitlab.com/inkscape/inbox/-/issues/2125

4. **An unmerged, experimental Inkscape branch** (MR !7675,
   https://gitlab.com/inkscape/inkscape/-/merge_requests/7675) adds a
   "Link (non-rasterized)" SVG import mode with a manual "Update Linked
   SVG" refresh action that preserves true vector fidelity. Status as of
   this conversation: unmerged, LLM-assisted implementation, several open
   TODOs (no "update all," no relink option, no docs), zero CI pipeline
   runs (no downloadable build). **User decided not to build this** --
   too much effort for an unreviewed, in-progress feature. A full
   Windows/MSYS2 build guide was written in case this changes later:
   `build_inkscape_linked_svg_branch.md` (should be attached alongside
   this file if continuing that thread).

5. **Adobe Illustrator comparison**: Illustrator's Links panel is
   genuinely more mature here -- flags "Update Available" automatically,
   one-click "Update Link"; placed linked vector files (AI/EPS/PDF) stay
   true vector through export (not rasterized); hyperlinks via Window >
   Attributes > Image Map, with a working "Preserve Hyperlinks" PDF export
   option (Inkscape's Cairo-based PDF export currently drops these,
   requiring a third-party tool called `svglinkify`). **User declined
   this route** due to Adobe subscription cost and not wanting to learn
   new software on top of Inkscape (which they already know well).

6. **Practical interim decision**: use Inkscape's raster "Link" import
   during active iteration (fast, auto-reload, resolution doesn't matter
   yet). Near final submission, optionally swap each figure to "Embed as
   vector" (delete + reimport, note the X/Y position from Inkscape's
   toolbar beforehand since the size will already match automatically --
   `figstyle.R`'s `save_fig()` already fixes physical width/height per
   figure, so only position needs to be reapplied manually). **User may
   skip this swap entirely** and submit with the raster-linked version,
   since most journals only enforce vector/high-res requirements at
   acceptance/proofing, not initial submission -- caveat: check the
   specific target journal's author guidelines, and keep rasterization
   resolution >=300 dpi even for review copies.

7. **Best current lead: browser-based PDF export bypasses the whole
   rasterization problem.** Chrome/Chromium renders a linked
   `<image href="child.svg">` as genuine vector content (not a raster
   snapshot), and Chrome's built-in headless print-to-pdf preserves that
   vector content in the resulting PDF -- sidestepping Inkscape's
   rasterizing PDF export entirely. Confirmed independently by a forum
   thread with someone in the *exact* same scenario (a "main" SVG figure
   linking several "secondary" plot SVGs for a scientific paper):
   https://inkscape.org/forums/questions/exporting-svg-with-linkedembedded-images-to-pdf-without-rasterising/
   Known snag: Chrome's print-to-pdf can default to fitting content to A4
   rather than the SVG's actual physical size; needs either the SVG's own
   width/height set in real units (in/mm), or a CSS `@page` rule via a
   small HTML wrapper. Also: this technique operates on a flat SVG canvas
   -- Inkscape's "Pages" are an Inkscape-specific construct a browser
   doesn't understand, so it needs to be applied per page (crop each
   page's `viewBox` into its own temp file), then merge the resulting
   per-page PDFs into one final file.

## Artifacts already built (in the outputs folder -- reattach these to
## the new session, a text summary alone won't carry the actual files)

- **`figstyle.R`** -- shared ggplot2 style module. Colorblind-safe
  Okabe-Ito palette (`scale_colour_paper()`/`scale_fill_paper()`),
  `theme_paper()`, standard figure-width constants
  (`fig_width_single`/`fig_width_double`/`fig_height_default`), and a
  `save_fig(plot, fig_id, width, height, root)` helper that always writes
  to `paper_figures/<fig_id>/<fig_id>.svg` via `svglite`, using
  `here::here()` for repo-root-relative pathing. Requires:
  `install.packages(c("ggplot2", "svglite", "here"))`.

- **`export_pages.py`** -- CLI prototype implementing finding #7 above.
  Parses `<inkscape:page>` geometry from a master SVG (namespace
  `http://www.inkscape.org/namespaces/inkscape`; falls back to treating
  the whole document as one page if no explicit Pages exist), computes
  each page's real physical size in inches, crops a copy of the SVG per
  page (sets `viewBox`/`width`/`height` on the root), writes temp files
  *next to* the master SVG (so relative links to per-figure SVGs still
  resolve), shells out to a local Chrome/Chromium install per page
  (`--headless=new --disable-gpu --print-to-pdf-no-header
  --print-to-pdf=...`), then merges all page PDFs via `pikepdf` into one
  final file. Auto-detects Chrome in common install locations (including
  the standard Windows path) or accepts `--chrome <path>`.
  Requires: `pip install lxml pikepdf`, plus a local Chrome/Chromium
  install.
  **Status: the SVG-parsing/page-cropping logic was tested successfully
  against a synthetic 2-page test file. The actual Chrome-rendering step
  is UNTESTED** -- no browser was available in the sandbox this was
  written in (no root access, and browser-automation packages like
  Playwright are blocked by that environment's policy). This needs a real
  test run on Zach's own Windows machine (where Chrome is installed) to
  check: (a) whether the output page comes out at the correct physical
  size rather than defaulting to A4, (b) whether the linked figure SVGs
  actually render as true vector (zoom into the PDF and check for
  crispness) rather than raster. Troubleshooting notes for the sizing
  issue are included at the bottom of the script itself.

- **`build_inkscape_linked_svg_branch.md`** -- step-by-step Windows/MSYS2
  build instructions for the unmerged Inkscape MR branch (finding #4).
  Not currently being pursued, kept for reference.
